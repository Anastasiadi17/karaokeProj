# Контекст проекта: AI-караоке платформа

> Стартовый документ для проекта в WebStorm. Описывает концепцию, юридические
> рамки, дифференциацию, монетизацию и требования к архитектуре. Не является
> юридической консультацией — перед запуском монетизации нужен юрист по IP.

---

## 1. Суть продукта

Веб-платформа для караоке и обработки вокала. Пользователь загружает своё
аудио, платформа обрабатывает его (разделение на дорожки, удаление вокала,
эффекты), пользователь записывает голос поверх, применяет AI-функции и
экспортирует результат.

Ключевой принцип: **платформа монетизирует обработку и AI, а не музыкальный
контент.** Это одновременно юридическая защита и продуктовая дифференциация.

### Целевой пользователь
- Любители петь (караоке дома, для соцсетей).
- Начинающие музыканты/ковер-исполнители, которым нужна минусовка и сведение.
- Контент-мейкеры, которым нужен быстрый обработанный вокал.

## 2. Юридические рамки (определяют архитектуру)

Использование чужих готовых фонограмм на коммерческом сервисе без лицензии
запрещено. Понадобились бы:
- лицензия на **авторские права** (композитор / автор текста — РАО в РФ или
  издатель);
- лицензия на **смежные права** (лейбл / исполнитель — на фонограмму).

Для караоке-сервиса это неподъёмные расходы и переговоры с каждым
правообладателем. Поэтому модель строится так:

**Разрешено / безопасно:**
- Пользователь загружает **своё** аудио → платформа обрабатывает → отдаёт
  обратно. Плата берётся за обработку, а не за песню.
- Каталог **royalty-free / production music** по лицензии (опционально, позже).
- AI-генерация фрагментов как обработка (не снимает прав на исходную мелодию,
  но и не распространяет её).

**Запрещено / рискованно:**
- Платный доступ к каталогу чужих песен.
- Хранение и перепродажа пользовательских загрузок.
- Монетизация чужого контента в любом виде.

**Обязательные механизмы:**
- Публичная оферта / Terms of Service: ответственность за легальность загрузки
  несёт пользователь.
- DMCA / процедура takedown для удаления по жалобе правообладателя.
- Обработанные файлы отдаются пользователю и **не** переиспользуются
  платформой; хранение — временное, с автоочисткой.

## 3. Дифференциация (фишка)

Обычные караоке-сервисы = текст + минусовка. Наша уникальность в **обработке и
AI**, что как раз обходит проблему прав. Сильная связка, редко встречающаяся
вместе:

1. **Браузерное / серверное разделение стемов** — пользователь грузит любой
   трек, платформа вытаскивает минусовку (vocal removal) и отдельные дорожки.
2. **Real-time обработка голоса** — авто-тюн, реверб, гармонизация, подстройка
   под тональность трека при записи.
3. **AI-достройка фрагментов** — вставить бридж, заполнить пропущенный участок,
   сгенерировать бэк-вокал в нужном месте.
4. **AI-оценка исполнения** — попадание в ноты, тайминг, скоринг как в играх.

Главная уникальная связка: **стем-сплиттинг + real-time голосовые эффекты +
AI-достройка фрагментов** в одном продукте.

## 4. Монетизация

Люди платят за **обработку, функции и AI**, а не за контент. Модель —
freemium + кредиты + разовые продажи.

### 4.1. Freemium-подписка (основа дохода)

| | Free | Pro — **$9,99/мес** |
|---|---|---|
| Разделение стемов | черновое, с артефактами | чистое, студийное |
| Число операций | 3 в месяц | fair-use 100 в месяц |
| Длина трека | целиком | целиком |
| Голосовые эффекты | базовые (реверб) | авто-тюн, гармонизация, проф. микс |
| Экспорт | с водяным знаком, сжатый | без знака, высокое качество (WAV/320kbps) |
| AI-кредиты | нет | +30% кредитов при покупке пакета (4.2) |

Граница Free должна: (а) показать ценность, (б) не разорять по вычислениям.
Ограничитель — **число операций**, а не длина трека: обрезка до минуты не даёт
услышать свою песню целиком и убивает главный аргумент к покупке, экономя при
этом около цента с операции.

### 4.2. AI-функции по кредитам (pay-per-use)

Дорогие в вычислениях операции продаются пачками кредитов. Базовая
единица: **1 кредит ≈ $0,10**, стартовый пакет — 100 кредитов за $9,99.

| Операция | Себестоимость | Цена | Наценка |
|---|---|---|---|
| Достройка / заполнение фрагмента | ~$0,068 | 3 кредита | ×4,4 |
| Генерация бэк-вокала | ~$0,068 | 3 кредита | ×4,4 |
| AI-мастеринг | ~$0,023 | 1 кредит | ×4,3 |

Пакета за $9,99 хватает примерно на 33 достройки фрагмента. Наценка ×4
покрывает холодные старты, неудачные генерации и повторы пользователя.

Подписчикам тот же пакет даёт +30% кредитов (связка удержания). Обоснование
себестоимости — в 4.5.

### 4.3. Разовые продажи

Готовый обработанный трек в студийном качестве — купить разово, без подписки.
Для тех, кому нужна одна запись.

### 4.4. Экономическая реальность (заложить сразу)

AI-операции = GPU-время, и оно тратится на **каждый** запуск. Но расчёт (4.5)
показал, что стоимость крайне неравномерна по типам операций — планировать
надо по самой дорогой, а не по средней.

| Класс операции | Себестоимость | Чем ограничивается |
|---|---|---|
| Разделение стемов | ~$0,005 | Практически ничем: шум на фоне подписки |
| AI-генерация (достройка, бэк-вокал) | ~$0,07 | Кредитами, наценка ×4 |
| Серверный real-time голоса | ~$0,064 за дубль | **Ничем — поэтому не делать** |

Отсюда принципы:

- **Free ограничивается числом операций, а не длиной трека.** При лимите
  3 операции/мес на полных треках Free-пользователь стоит $0,015/мес на общей
  модели и $0,003/мес на удешевлённой (4.6). На старте работает первый вариант:
  10 000 бесплатных пользователей = $150/мес. К 100 000 набегает $1 500/мес —
  около 8% валовой выручки; это терпимо настолько, что 4.6 включается не
  раньше 50 000 бесплатных пользователей. Урезание длины трека сэкономило бы
  две трети этой суммы ценой главного аргумента к покупке — тем более не стоит
  того.
- **Подписка $9,99 покрывает вычисления с запасом:** валовая маржа ≈98%, выход
  в ноль на ~1 900 разделениях в месяц. Fair-use потолок нужен против абьюза, а
  не против расходов.
- **Дорогое — только генеративный AI.** Оно продаётся по кредитам с наценкой
  ×4 (4.2) и не входит в подписку безлимитно.
- **Real-time обработка голоса делается на клиенте.** Серверный вариант держит
  GPU всю сессию записи и масштабируется от числа поющих, а не от объёма
  вычислений; подписка не покрывает такое ни при какой цене.
- **Хранилище — только с нулевым egress** (R2 / Backblaze B2). На S3 отдача
  стемов стоит столько же, сколько сам GPU.
- **Юнит-экономику пересчитывать** при смене провайдера, модели или железа:
  цены на GPU меняются быстро, расчёт 4.5 привязан к августу 2026.
- Реклама на старте не окупает серверные затраты — опора на подписку и кредиты.

### 4.5. Юнит-экономика разделения стемов (расчёт)

Расчёт от августа 2026, денежные таблицы пересчитаны 14 августа под замер
времени обработки. Цены на GPU и API меняются — пересчитывать перед запуском.

#### Допущения

| Параметр | Значение |
|---|---|
| Средний трек | 3,5 мин стерео |
| Модель | Demucs v4 (htdemucs), 4 стема |
| Железо | RTX 4090, RunPod Serverless — $1,10/час активного времени |
| Время обработки | ≈9 с оплачиваемого GPU-времени на 3,5-мин трек: 6,4 с в прогретом контейнере плюс усреднённая надбавка за холодные старты — см. разбор |
| Эффективная утилизация | 70% (холодные старты, очередь) |
| Хранилище | Cloudflare R2, $0,015/ГБ-мес, egress $0 |

**Время обработки измерено, и измерено на двух длительностях** — это
оказалось важнее самого числа. Опубликованные бенчмарки разбросаны: от ~2,7 с
чистого GPU-компьюта на TensorRT-сборке до ~89 с на слабой T4. Локальный
замер (RTX 5060, torch 2.11.0+cu128, demucs 4.1.0, htdemucs, обычный
`apply_model` без TensorRT) дал две точки: клип 30 с → 3,5 с, клип 600 с
(`max_duration_sec`, потолок сервиса) → 20,9 с. Прямая по ним имеет
постоянную составляющую ≈2,6 с и наклон ≈0,0305 с на секунду звука.
**Отсюда 3,5-минутный трек — около 9 с.**

**Экстраполяция с одного 30-секундного клипа завышает**, потому что тянет
линейно и постоянную составляющую тоже. Ошибка растёт с длиной: на 3,5-мин
треке пропорция даёт ≈24,5 с против модельных 9 с (в 2,7 раза), на предельных
600 с — ≈70 с против фактических 20,9 с (в 3,3 раза, и это уже прямой замер, а
не расчёт). Прежняя редакция этого раздела считала именно пропорцией и
получала ≈24–25 с на трек — число опровергнуто замером из той же ветки и
оставлено здесь только как объяснение, откуда взялось допущение в таблице.

Постоянная составляющая — это загрузка весов из локального кеша и перенос на
GPU: таймер стартует до `_ensure_model()`, поэтому в замер она входит. То
есть это первый вызов на процесс, а не «модель уже в памяти GPU от
предыдущего запроса». Разброс тёплых прогонов на 30-секундном клипе: 10 из 11
уложились в 3,4–3,9 с, один дал 6,0 с — вероятно, фоновая нагрузка на GPU от
других процессов этой десктопной машины (браузер, оверлеи), не выделенный
сервер. Карта здесь RTX 5060, а таблица допущений построена на RTX 4090 —
замер делался на доступном локально железе, которое заметно слабее, так что
для 4090 оценка остаётся консервативной с запасом.

**Видеопамяти хватает с девятикратным запасом.** На предельных 600 с пик
`max_memory_allocated` — 0,76 ГиБ (`max_memory_reserved` 0,90) из 7,96 ГиБ
карты, откат на CPU не срабатывал ни разу. Опасение, что денормировка всех
четырёх стемов (`sources * std + mean`, ≈846 МБ на копию) раздует
видеопамять, не подтвердилось: копии живут в оперативной памяти. Host-RAM
этим замером не измерялась.

**Денежные таблицы пересчитаны под замер 14 августа 2026.** Механически делить
прежние числа на три было нельзя: 9 с — это первый вызов в процессе, а раздел
описывает RunPod Serverless, где контейнеры поднимаются холодными. Поэтому
оплачиваемое время собрано из трёх слагаемых, каждое со своим поведением:

| Слагаемое | Сколько | Когда платится |
|---|---|---|
| Инференс с I/O | 0,0305 с на секунду звука → **6,4 с** на 3,5 мин | Каждый запрос |
| Загрузка весов на GPU | **2,6 с** | Первый запрос в процессе |
| JIT-компиляция ядер CUDA/cuDNN | **≈20 с** | Первый запрос в контейнере без прогретого кеша |

Прогрев модели на старте (реализован в API: раннер поднимает разделитель до
первой задачи) переносит второе и третье слагаемые из времени запроса во
время старта контейнера. На RunPod это время всё равно оплачивается, поэтому
в расчёте оно остаётся — но платится один раз на контейнер, а не на запрос.

При доле холодных стартов *c* оплачиваемое время запроса — `6,4 + c × 22,6`:

| Доля холодных стартов | Оплачиваемое время | GPU за операцию (÷0,7) |
|---|---|---|
| 5% | 7,5 с | $0,0033 |
| **10% (базовое допущение)** | **8,7 ≈ 9 с** | **$0,0039** |
| 20% | 10,9 с | $0,0048 |

Базовые 10% — допущение, а не замер: реальная доля зависит от плотности
трафика и настроек scale-down, и её надо снять на живом пуле. Вся вилка
укладывается в $0,003–0,005 на операцию, то есть вывод раздела от неё не
зависит.

Совпадение с числом «≈9 с на трек» из замера — случайное, и путать их не надо:
там это первый вызов в процессе (2,6 + 6,4), здесь — усреднённый счёт за
запрос (6,4 плюс размазанные по запросам холодные старты). Числа сошлись
потому, что доля холодных стартов взята небольшой.

**Коэффициент утилизации 70% оставлен прежним**, хотя холодные старты из него
теперь вынесены в явное слагаемое. Ему остаётся простой контейнера до
scale-down и очередь; 30% на это — с запасом. Уменьшать коэффициент без
замера на реальном пуле значило бы подгонять расчёт под желаемое.

**Отдельно — холодный старт, факт, который таблица допущений не должна
прятать.** Самый первый настоящий инференс на этой машине (сразу после
установки cu128-сборки, ещё не заполненный кеш CUDA/cuDNN JIT-компиляции
ядер) дал 23,8 с на том же 30-секундном клипе против тёплых 3,5 с. Разница
≈20 с — это компиляция ядер, издержки одноразовые и **от длины аудио не
зависят**, поэтому умножать их на 7 вместе со всем остальным (как делала
прежняя редакция, получая ≈167 с) — та же ошибка, что и в основном расчёте.
Правильная прикидка холодного 3,5-минутного трека — тёплые ≈9 с плюс ≈20 с
компиляции, то есть **≈29 с**; прямым замером на такой длительности это не
проверялось. На этой машине платят их один раз: драйвер кеширует
скомпилированные ядра на диск, и повторные запуски (даже в новом процессе
Python) на них больше не попадают. Раздел описывает именно **RunPod
Serverless**, где контейнер поднимается холодным на каждый cold start — если
его образ не несёт прогретый PTX/cuDNN-кеш, первый запрос в свежем
контейнере платит эти ≈20 с целиком. Раньше эта надбавка пряталась в
коэффициенте утилизации 70% («холодные старты, очередь»), хотя он на неё не
рассчитывался: коэффициент дисконтирует простаивающие GPU-секунды между
заданиями, а не задержку конкретного холодного запроса — это две разные
величины, и одна не покрывает другую. **В пересчёте от 14 августа надбавка
вынесена в явное слагаемое** (таблица ниже), и коэффициент отвечает только за
простой.

Для человека, ждущего результат, остаётся отдельный вывод: первый запрос в
свежем контейнере идёт ≈29 с вместо ≈9 с — заметно, но это не «до 167 с», как
писала прежняя редакция. Лечится прогретым PTX/cuDNN-кешем в образе; тогда
холодный запрос теряет только 2,6 с на загрузку весов.

#### Сравнение путей

| Путь | Цена за операцию | Комментарий |
|---|---|---|
| **Свой GPU, serverless 4090** | **$0,005** | Базовый вариант, нужен DevOps |
| Свой GPU, выделенный под ($0,69/ч) | $0,0017 при 100% загрузки → $0,017 при 10% | Под стоит $497/мес всегда, даже пустой |
| Replicate (готовый demucs) | $0,020 | Внешняя цена, с нашим замером не связана |
| Готовые API (LALAL.AI, StemSplit) | $0,14–0,35 | В 30–70 раз дороже, только для прототипа |

Выделенный под выигрывает у serverless по-прежнему при загрузке выше ~45%:
порог держится на отношении цен часа и от скорости обработки не зависит. А вот
в операциях он сдвинулся втрое — теперь это около **4 250 операций в сутки**
против прежних 1 500, потому что тот же под успевает больше.

**Замер сместил и сравнение с Replicate.** Раньше готовый сервис стоил +30% к
своей инфраструктуре, теперь — вчетверо дороже. Но $0,015 разницы на операцию
— это $15 на тысячу операций: DevOps-возня вокруг своего serverless окупается
такой ставкой очень нескоро. Практический вывод не изменился, а усилился:
**на старте брать Replicate и не строить свой пул**, пока объёмы не выйдут за
несколько тысяч операций в сутки.

#### Разбор базового варианта

```
GPU:  9 с × $0,000306/с            = $0,0028
      ÷ 0,7 (утилизация)           = $0,0039
Хранение: ~100 МБ × 24 ч на R2     = $0,0001
Egress (R2)                        = $0,0000
Очередь, API, логи, накладные      = $0,0010
─────────────────────────────────────────────
ИТОГО                              ≈ $0,004–0,006
```

**Структура расходов сдвинулась.** При 25 с на GPU приходилось ~90%
себестоимости, теперь ~78%, а накладные на запрос выросли с 8% до 20% суммы.
Дальше выжимать секунды инференса малополезно: следующий выигрыш уходит уже
не в вычисления, а в очередь, логи и операции с хранилищем.

**Выбор хранилища двигает себестоимость на 60%.** На S3 те же 100 МБ отдачи
стоят $0,009 egress — почти столько же, сколько сам GPU. R2 / Backblaze B2 с
нулевым egress — не оптимизация, а обязательное условие.

#### Следствия для тарифов

Главный вывод корректирует 4.4: **разделение стемов — не дорогая операция.**
Полцента против подписки в $10 — это шум. Опасение «рост пользователей = рост
убытков» на этом участке не подтверждается.

- **Free.** Лимит 3 операции/мес, трек целиком = $0,015/пользователя/мес на
  общей модели htdemucs. 100 000 бесплатных пользователей → ~$1 500/мес
  компьюта; при конверсии 2% они дают 2 000 подписчиков ≈ $18 800/мес net,
  то есть **Free съедает ~8% валовой выручки** вместо прежних ~24%. Это уже
  не отдельная статья расходов, а накладные: до перевода Free на дешёвую
  модель (4.6) можно спокойно жить очень долго — порог целесообразности
  отодвинулся с 15 000 бесплатных пользователей до ~50 000.
  Ограничитель тарифа — **число операций**: себестоимость масштабируется с
  длиной аудио примерно линейно, но в абсолюте разница между минутой и полным
  треком — доли цента за операцию, несопоставимые с уроном демонстрации
  ценности.
- **Pro $9,99.** Комиссия Stripe $0,59 → net $9,40. Реальный подписчик делает
  20–40 разделений/мес = $0,10–0,20 компьюта. **Валовая маржа ≈ 98%.** В ноль
  тариф уходит на ~1 900 операциях в месяц — это 63 разделения каждый день без
  выходных, то есть живой человек до него не доберётся физически. Fair-use
  потолок 100 операций/мес теперь защищает не от расходов, а только от
  автоматизированного абьюза, — и это единственное, зачем он нужен.
- **Разовая продажа (4.3).** Себестоимость трека «под ключ» упала примерно до
  $0,02. Вывод от этого не изменился ни на цент: фиксированные $0,30 комиссии
  съедают 33% с чека в $0,99, и **минимальная разовая цена остаётся $2,99**.
  Здесь цену диктует платёжный провайдер, а не GPU, — и никакое ускорение
  модели этого не сдвинет.

#### Главный риск — не разделение стемов

Разделение стоит $0,005, AI-генерация — $0,07: в 14 раз дороже, но управляемо
через кредиты. Пересчёт разнёс эти две статьи ещё дальше друг от друга —
планировать по средней стоимости операции стало откровенно бессмысленно.

Опасность в другом. Если **real-time обработку голоса делать на сервере**, GPU
держится открытым всю сессию записи: 3,5 мин × $0,000306/с = **$0,064 за один
дубль**. Десять дублей — $0,64, больше, чем весь месячный компьют платного
подписчика. Масштабируется это не от объёма вычислений, а от того, сколько
человек поёт, — никакая подписка такое не покрывает.

**Вывод: авто-тюн, реверб и гармонизация обязаны считаться на клиенте**
(Web Audio API + AudioWorklet + WASM) — все три там реализуемы. Серверный
real-time убивает юнит-экономику вернее всего остального в проекте.

### 4.6. Удешевление Free: отдельная модель

Как снизить себестоимость бесплатного тарифа, не трогая длину трека.
Считалось вместе с 4.5, те же допущения.

#### Дешёвое железо не работает

Очевидный ход — гонять Free на слабой карте — экономики не даёт: цена
GPU-часа и скорость масштабируются вместе.

| Железо | Цена/час | htdemucs, 3,5 мин | Стоимость операции |
|---|---|---|---|
| RTX 4090 serverless | $1,10 | ~9 с | $0,0028 |
| L4 serverless | ~$0,60 | ~20 с | $0,0033 |

На «дешёвой» L4 операция выходит **дороже**: карта вдвое с лишним медленнее, а
стоит вдвое меньше. У современных GPU price/performance лучше, чем у старых.
**Экономия возможна только в модели, не в железе.**

Числа пересчитаны 14 августа 2026 под замер из 4.5. Строка 4090 — оплачиваемое
время оттуда же; строка L4 получена переносом прежнего соотношения скоростей
(L4 медленнее в 2,2 раза) на новое число, то есть это оценка, а не замер.
Отсюда честная оговорка: **разрыв в 20% между картами пересчёт не проверяет** —
он в этой таблице сохраняется по построению, потому что оба столбца
масштабировались одним множителем. Вывод «экономия в модели, не в железе»
держится на соотношении цен и скоростей из внешнего бенчмарка; чтобы он стал
замером, нужен прогон htdemucs на самой L4.

#### Free на Spleeter (2 стема)

Free нужен ровно один результат — минусовка, то есть 2 стема вместо 4. Здесь
работает Spleeter: ~100× realtime на GPU против ~8× у htdemucs.

| Параметр | Free (Spleeter 2-stem) | Pro (htdemucs 4-stem) |
|---|---|---|
| Инференс с I/O, прогретый контейнер | ~2,1 с | ~6,4 с |
| Оплачиваемое время с холодными стартами | ~6 с | ~9 с |
| Железо | RTX A4000-класс, ~$0,27/ч | RTX 4090, $1,10/ч |
| GPU при 70% утилизации | $0,00064 | $0,0039 |
| Хранение (2 стема MP3 128k, 24 ч) | $0,0001 | $0,0001 |
| Накладные (очередь, R2-операции, логи) | $0,0003 | $0,0010 |
| **Итого за операцию** | **≈ $0,001** | **≈ $0,005** |

Разница была больше чем на порядок, после пересчёта — впятеро. Колонка Free
осталась прежней: числа Spleeter взяты из внешнего бенчмарка и от нашего
замера htdemucs не зависят. На L4 вместо A4000 Free-операция стоила бы
$0,0015, тоже приемлемо; точная цифра зависит от того, какие карты реально
доступны в serverless-пуле.

Структурный момент: при $0,001 за операцию GPU перестаёт быть главной статьёй
— накладные расходы на запрос уже сопоставимы с вычислениями. Дальше
оптимизировать модель бессмысленно. **После пересчёта это верно и для
htdemucs**: там накладные — пятая часть себестоимости, и вторая модель
экономит уже не порядок, а $0,004 на операцию.

#### Что это даёт тарифу

| | Одна модель для всех | Раздельные модели |
|---|---|---|
| Себестоимость Free-пользователя | $0,015/мес | **$0,003/мес** |
| 100 000 free-пользователей | $1 500/мес | **$300/мес** |
| Доля Free в валовой выручке | ~8% | **~1,6%** |

Разделение моделей даёт ту же экономию, что обрезка трека до минуты, но без
ущерба продукту — ровно тот размен, который забракован в 4.4.

Пересчёт съел главный аргумент этого раздела. Раньше речь шла о четверти
валовой выручки — сумме, ради которой строят второй пул воркеров. Теперь
разница между «одной моделью» и «раздельными» — 6,4 процентных пункта
выручки, и вопрос из «когда это строить» превращается в «стоит ли вообще».

#### Продуктовая сторона

Качество Spleeter по SDR на 30–40% ниже htdemucs: слышны водянистые остатки
вокала, тарелки протекают в минусовку. Для пения дома этого достаточно —
артефакты маскируются собственным голосом. Но при критическом прослушивании
или попытке выложить результат разница очевидна. Это ровно та сегментация,
которая записана в 4.1 как «черновое, с артефактами» против «чистое,
студийное»: Free реально работает, а не сломан искусственно.

Риск в обратную сторону: для чистого караоке Spleeter может оказаться
*достаточно хорош*, и апгрейд перестанет мотивироваться качеством. Тогда
работают три остальных рычага — 3 операции в месяц, водяной знак, отсутствие
AI-кредитов.

#### Когда это строить

**Не на MVP.** Вторая модель — это второй контейнер, второй пул воркеров и
второй набор того, что ломается: около полутора недель работы плюс постоянное
обслуживание.

Экономия = `число free-пользователей × $0,012/мес` (было $0,042 до пересчёта).
Первый год стоит около $7,5 тыс. — полторы недели работы плюс обслуживание.
Отсюда пороги:

| Порог | Free-пользователей | Было до пересчёта |
|---|---|---|
| Окупается только обслуживание (~$200/мес) | ~16 700 | ~4 800 |
| Возврат разработки в пределах года | **~52 000** | ~15 000 |

Практический вывод: запускаться на htdemucs для всех, а Spleeter-путь для Free
отложить до бесплатной аудитории порядка **50 тысяч** — втрое дальше, чем
считалось. До этого порога расходы на Free незначительны: при 10 000
пользователей это $150/мес, при 30 000 — $450/мес, то есть меньше, чем стоит
один инженер-день в месяц на поддержку второго пула.

Побочное следствие: к моменту, когда порог станет актуальным, аргументом за
вторую модель будет скорее не экономия, а нагрузочная развязка Free и Pro —
и решать надо будет уже по ней, а не по этой таблице.

## 5. Требования к архитектуре (для проработки в WebStorm)

Ниже — не финальные решения, а требования, под которые выбираются стек и
архитектура.

**Функциональные блоки:**
- Загрузка аудио (валидация формата, размера, длины по тарифу).
- Пайплайн обработки: разделение стемов, vocal removal, эффекты.
- Запись голоса в браузере поверх дорожки, синхронизация/latency.
- Real-time эффекты (авто-тюн, реверб, гармонизация).
- AI-модуль: достройка фрагментов, бэк-вокал, мастеринг.
- Сведение и экспорт (форматы/качество по тарифу, водяной знак для Free).
- Аккаунты, тарифы, биллинг, кредитная система.
- Хранилище с временным хранением и автоочисткой + DMCA-takedown.

**Нефункциональные требования:**
- Тяжёлая обработка — асинхронно (очередь задач, воркеры), а не в запросе.
- GPU-операции изолированы и метрируются (учёт стоимости на пользователя).
- Учёт latency при записи в браузере (Web Audio API / AudioWorklet).
- **Real-time голосовые эффекты — только на клиенте** (Web Audio /
  AudioWorklet / WASM). Серверный real-time держит GPU всю сессию записи и
  ломает юнит-экономику — см. 4.5.
- Хранилище — только с нулевым egress (R2 / Backblaze B2): на S3 отдача
  стемов стоит столько же, сколько сам GPU (см. 4.5).
- Ограничения по тарифу проверяются на сервере, не только в UI.
- Масштабируемость обработки независимо от фронтенда.

**Вопросы к проработке в WebStorm:**
- Фронтенд: фреймворк, Web Audio API / AudioWorklet / WASM для DSP.
- Разделение стемов: своя модель (Demucs/Spleeter-класс) vs внешний API —
  считать стоимость и качество.
- Очередь и воркеры: инфраструктура фоновой обработки.
- AI-функции: свои модели vs внешние API (в т.ч. Anthropic API для оркестрации).
- Биллинг: платёжный провайдер, учёт кредитов, подписки.
- Хранилище: временные файлы, автоочистка, соответствие takedown-процедуре.
