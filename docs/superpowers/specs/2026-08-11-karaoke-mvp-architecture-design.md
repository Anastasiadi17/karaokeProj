# Дизайн: MVP AI-караоке платформы (локальный срез)

Дата: 2026-08-11
Статус: на вычитку
Источник требований: `karaoke-context.md`, разделы 4.5, 4.6, 5, 6

---

## 1. Объём

Проектируется MVP из раздела 6 контекстного документа: **ядро обработки (A)**
и **браузерная студия (B)**. Полный продукт состоит из четырёх независимых
подсистем, и остальные две проектируются отдельными циклами:

| Подсистема | В этом спеке | Зависимости |
|---|---|---|
| A. Ядро обработки | **да** | нет |
| B. Браузерная студия | **да** | A, по контракту «дай минусовку» |
| C. Аккаунты и биллинг | нет | нет |
| D. AI-модуль | нет | A инфраструктурно, C по кредитам |

**Цепочка MVP:** загрузка трека → отделение минусовки → запись голоса поверх →
сведение → экспорт с водяным знаком.

### Что явно не входит

Аккаунты, платежи, кредиты, тарифные лимиты, AI-функции, авто-тюн,
гармонизация, тексты песен с таймкодами, оценка исполнения, каталог
royalty-free, DMCA-процедура, деплой в сеть.

Отсутствие аккаунтов и DMCA допустимо только потому, что MVP не выходит в
сеть. Первый же публичный доступ требует их обоих — см. раздел 2 контекстного
документа.

## 2. Решения, принятые на входе

| Решение | Выбор | Обоснование |
|---|---|---|
| Разделение стемов | локально, потом внешний API | итерация бесплатна, миграция за швом |
| Развёртывание | localhost, границы как в проде | деплой = смена реализаций, не переписывание |
| Эффекты в студии | запись + реверб + экспорт | авто-тюн — отдельный крупный кусок |
| Стек | FastAPI + Vite/React | сервер тонкий, клиент толстый |
| Автор кода | агент, ревью человеком | жёсткие границы модулей, тесты, мейнстрим-стек |

**Компенсация задержки записи не является опцией.** Браузер добавляет 50–200 мс
между воспроизведением и захватом; без вычитания этой задержки запись негодна
всегда, а не иногда.

### Целевое железо

RTX 5060 (8 ГБ, Blackwell, sm_120), i5-14400F, 16 ГБ RAM, Windows 10.

Видеопамяти для htdemucs достаточно с запасом. **Критично:** sm_120 требует
сборки PyTorch под CUDA 12.8 или новее. Обычный `pip install torch` ставит
несовместимую сборку, которая падает с «no kernel image is available» либо
молча уходит на CPU — там трек считается минутами вместо секунд.

## 3. Архитектура

Два приложения в одном репозитории, между ними только HTTP.

```
karaokeProj/
├── api/                          FastAPI + обработка
│   ├── src/karaoke_api/
│   │   ├── main.py               роуты, старт, проверка GPU
│   │   ├── config.py             настройки из .env
│   │   ├── jobs/
│   │   │   ├── models.py         Job, JobStatus, Stage
│   │   │   ├── store.py          SQLite-репозиторий
│   │   │   └── runner.py         фоновый исполнитель
│   │   ├── separation/
│   │   │   ├── base.py           StemSeparator (Protocol)
│   │   │   └── demucs_local.py   локальная реализация
│   │   ├── storage/
│   │   │   ├── base.py           Storage (Protocol)
│   │   │   └── local.py          файловая система
│   │   └── audio/probe.py        валидация формата и длительности
│   ├── tests/
│   └── pyproject.toml
├── web/                          Vite + React + TS
│   ├── src/
│   │   ├── audio/                ядро студии, без React
│   │   │   ├── latency.ts        оценка и хранение смещения
│   │   │   ├── recorder.ts       AudioWorklet-захват
│   │   │   ├── reverb.ts         синтетическая импульсная характеристика
│   │   │   ├── mixdown.ts        офлайн-сведение
│   │   │   ├── watermark.ts      генерация маркера
│   │   │   └── encode.ts         WAV-энкодер
│   │   ├── features/             upload · processing · studio
│   │   ├── api/                  типизированный клиент
│   │   └── ui/
│   ├── tests/
│   └── package.json
├── data/                         рабочие файлы, в .gitignore
└── docs/superpowers/specs/
```

### Два принципа структуры

**`web/src/audio/` не знает про React.** Чистый модуль поверх Web Audio: на
вход буферы и параметры, на выход буферы. React в `features/` держит только
состояние интерфейса. Это условие проверяемости: размазанный по компонентам
аудиокод нельзя ни протестировать, ни отладить.

**`separation/` и `storage/` описаны протоколами.** Не абстракция ради
абстракции — переход на внешний API запланирован в 4.5 и должен стоить один
новый файл плюс строку конфига.

### Три шва

| Шов | Сейчас | Потом |
|---|---|---|
| `StemSeparator` (`separation/base.py`) | локальный demucs | Replicate / свой GPU-пул |
| `Storage` (`storage/base.py`) | папка `data/` | R2 / S3 |
| Очередь (`jobs/store.py` + `jobs/runner.py`) | SQLite + фоновая задача | Redis, отдельные воркеры |

Шов — это интерфейс, а не инфраструктура. Redis, Celery, Docker и миграции БД
на одного пользователя дают расходы без отдачи и в MVP не входят.

## 4. Поток данных и контракт API

```
браузер                          api                        диск
   │ POST /api/tracks (файл)
   ├──────────────────────────────▶ валидация
   │ 201 {track_id, job_id}              ├──▶ сохранён оригинал
   ◀──────────────────────────────┤      │
   │ GET /api/jobs/{id}  раз в сек.      │ runner: demucs --two-stems
   ├──────────────────────────────▶      │  (модель уже в памяти)
   │ {stage, progress}                   ├──▶ vocals.wav, no_vocals.wav
   ◀──────────────────────────────┤      │
   │ GET .../stems/no_vocals             │
   ◀━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┤ Range поддержан
   │
   │  дальше сервер не участвует:
   │  калибровка → запись → сведение → экспорт
```

**Голос не уходит на сервер.** Запись, сведение и кодирование целиком в
браузере, результат отдаётся через `<a download>`. Это совпадает с юридической
рамкой раздела 2: пользовательских записей у платформы физически нет.

**Режим `--two-stems=vocals`.** htdemucs внутри считает четыре дорожки и сам
складывает их в минусовку. Для караоке нужны ровно `vocals` и `no_vocals`.

**Опрос вместо SSE.** Раз в секунду до `done`. На одного пользователя SSE —
лишний слой; шов для смены транспорта уже есть.

### Модель данных (SQLite, без миграций на старте)

| Таблица | Поля |
|---|---|
| `tracks` | id, filename, storage_key, duration_sec, created_at |
| `jobs` | id, track_id, status, stage, progress, error_message, result_json, timestamps |

`result_json` хранит ключи стемов и пометку о деградации: `{"stems": {"vocals": "...", "no_vocals": "..."}, "degraded": false}`

**Статус и стадия — разные поля.** `status` ∈ `{queued, running, done, failed}`
описывает судьбу задачи; `stage` ∈ `{loading, separating, writing}` осмыслен
только при `status = running` и в остальных состояниях равен `null`. Прогресс
из demucs относится только к стадии `separating`, поэтому интерфейс показывает
стадии, а не одну линейную полоску на тридцать секунд.

### Лимиты загрузки (значения по умолчанию в конфиге)

| Параметр | Значение |
|---|---|
| Форматы | mp3, wav, m4a, flac |
| Максимальная длительность | 10 мин |
| Максимальный размер | 100 МБ |
| TTL файлов в `data/` | 24 ч |

Формат определяется разбором содержимого, а не расширением файла.

### Эндпоинты

```
POST   /api/tracks                    → 201 {track_id, job_id}
                                      → 400 unsupported_format | too_long | too_large
GET    /api/jobs/{job_id}             → 200 {status, stage, progress, error?, result?}
GET    /api/tracks/{id}/stems/{kind}  → 200 audio/wav, Range обязателен
DELETE /api/tracks/{id}               → 204
```

Range-запросы обязательны: без них браузер не перематывает длинный WAV.

## 5. Аудиодвижок

### Компенсация задержки

Сдвиг применяется **при сведении**, а не в реальном времени: пишем сырой поток,
при сведении сдвигаем записанный буфер на N сэмплов назад. Точно, отлаживаемо и
позволяет менять смещение после записи, не переписывая дубль.

Значение берётся в два шага:

1. Автооценка из `outputLatency + baseLatency` — стартовая точка.
2. Ползунок ±200 мс с мгновенным прослушиванием результата.

Значение хранится в localStorage — калибруется один раз на устройство.

Автокалибровка по кросс-корреляции тестового импульса точнее, но требует петли
через динамики и несовместима с наушниками. Заложена отдельной задачей на
случай, если ползунок окажется мучением.

### Захват

Через `AudioWorkletNode`, а не `MediaRecorder`: последний отдаёт сжатый webm с
неопределённым таймингом, непригодный для выравнивания. Воркет складывает сырые
Float32-кадры с точным счётом сэмплов.

**Три флага `getUserMedia` обязательно в `false`:** `echoCancellation`,
`noiseSuppression`, `autoGainControl`. По умолчанию браузер их включает — они
рассчитаны на речь, режут певческий диапазон, качают громкость и добавляют
плавающую задержку, ломающую любую компенсацию.

### Граф

```
       ┌── dry gain ──────────────┐
mic ───┤                          ├──▶ мониторинг (переключаемый)
       └── convolver ── wet gain ─┘

mic ──▶ worklet ──▶ Float32 буфер ──┐  сдвиг на −latency
no_vocals.wav ─────────────────────┐│
                                   ▼▼
                          OfflineAudioContext
                     голос(dry+wet) + музыка + знак
                                    ▼
                            WAV без зависимостей
```

**Реверб** — `ConvolverNode` с синтетической импульсной характеристикой
(затухающий шум, генерируется кодом). Внешние IR-файлы не нужны, лицензировать
нечего.

**Мониторинг переключаемый.** Круг через Web Audio добавляет 20–40 мс при
слышимом пороге около 15–20. Часть людей это раздражает сильнее, чем пение
всухую, поэтому решение остаётся за пользователем.

**Водяной знак** — короткий синтезированный маркер в начале и далее раз в 30
секунд на −18 dB, ещё один источник в офлайн-графе.

**Экспорт** — WAV, заголовок плюс PCM, без библиотек. MP3 потребовал бы
wasm-кодек ради экономии места, которая на localhost не нужна.

## 6. Ошибки и граничные случаи

**Проверка GPU при старте, а не на первой задаче.** API гоняет пробный тензор;
при неудаче пишет в лог причину и нужный индекс пакетов, продолжает на CPU с
явным предупреждением в интерфейсе. Иначе проблема установки проявится как
«задача упала» через три недели.

**Нехватка видеопамяти — откат, а не падение.** Ловим `CUDA out of memory`,
повторяем на CPU, помечаем задачу выполненной с пометкой о деградации.

**Задачи, пережившие смерть процесса.** При старте всё в статусе `running`
помечается `failed`. Воркер один, воскрешать нечего; честное «упало, запусти
заново» лучше вечно висящей задачи.

**Одна частота дискретизации на весь граф.** Микрофон обычно 48 кГц, трек часто
44,1. Создаём `AudioContext({sampleRate})` под частоту трека — браузер
ресемплит вход сам. Иначе рассинхрон накапливается по длине песни и проявляется
как медленно уползающий голос.

**Клиент:** отказ в доступе к микрофону объясняется текстом; клиппинг
показывается сразу, а не после сведения; уход со страницы с несохранённой
записью перехватывается `beforeunload`.

Оговорка: `beforeunload` — слабая защита, браузер вправе её проигнорировать.
Надёжный вариант — складывать буфер в IndexedDB. В MVP не входит; первый
кандидат на добавление, если при обкатке начнутся потери дублей.

**Автоочистка `data/`** по TTL из конфига, при старте и раз в час.

## 7. Тестирование

Раз код пишет агент, тесты — основной механизм контроля. Два фейка делают
быстрым почти всё.

**`FakeSeparator` снимает GPU с критического пути.** Реализация протокола,
копирующая заготовленные файлы. Весь серверный конвейер — загрузка, валидация,
очередь, смена стадий, выдача стемов, автоочистка — тестируется через
`TestClient` за миллисекунды и детерминированно.

Настоящий demucs остаётся в одном медленном тесте под маркером `slow`,
исключённом из прогона по умолчанию. Этот тест работает измерительным прибором:
печатает фактическое время обработки — то число, которое в 4.5 записано как
допущение «25 секунд, обязательно замерить».

**Тест на выравнивание — главный в проекте.** Синтетический трек со щелчком на
известной позиции и «запись» с тем же щелчком, сдвинутым на известную задержку.
После сведения с компенсацией щелчки обязаны совпасть с точностью до сэмплов.
Это превращает самую субъективную часть системы в детерминированное
утверждение; без него регрессия в компенсации обнаруживается только ухом и
только случайно.

| Что | Чем | Скорость |
|---|---|---|
| Валидация, очередь, роуты | pytest + TestClient + FakeSeparator | быстро |
| WAV-энкодер, генерация IR, расчёт сдвига | Vitest в Node | быстро |
| Сведение, реверб, выравнивание | Vitest в headless Chromium, настоящий `OfflineAudioContext` | быстро |
| Реальный demucs | pytest, маркер `slow` | вручную |
| Путь целиком | Playwright с подменённым микрофоном | в CI |

Playwright работает всерьёз: Chromium подменяет устройство захвата файлом
(`--use-file-for-fake-audio-capture`), поэтому сценарий «загрузил → дождался →
записал → скачал» прогоняется без человека.

**Не тестируется автоматически:** живой микрофон, качество звучания, подробная
вёрстка. Для них чек-лист ручной проверки в репозитории.

## 8. Критерии готовности

1. Загруженный трек проходит путь до скачанного файла без ручных шагов.
2. Тест на выравнивание проходит; голос в экспорте попадает в музыку на слух.
3. Медленный тест напечатал фактическое время обработки на RTX 5060, и число
   внесено в раздел 4.5 контекстного документа вместо допущения.
4. Быстрые тесты зелёные и не требуют GPU.
5. Проект поднимается одной командой на чистой машине по README.

Пункт 3 — единственный, ради которого MVP вообще нужен с точки зрения бизнеса:
он закрывает главную дыру в юнит-экономике.

**Проверку спроса этот MVP не выполняет** — на localhost её выполнить нельзя.
Раздел 6 контекстного документа ставит MVP обе цели сразу; здесь достигается
только вторая. Проверка спроса требует публичного доступа, а значит аккаунтов,
лимитов и DMCA — то есть подсистемы C.

## 9. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| PyTorch не заводится на sm_120 | высокая | проверка при старте, откат на CPU, инструкция в README |
| Мониторинг с задержкой раздражает | средняя | переключатель; при провале — отказ от браузерного монитора |
| Ползунок калибровки мучителен | средняя | автокалибровка по импульсу как следующая задача |
| Потеря дубля при обновлении страницы | средняя | `beforeunload`; при повторении — IndexedDB |
| Фактическое время обработки сильно выше 25 с | низкая | пересчёт 4.5 и 4.6 от факта |

## 10. Открытые вопросы

Единственный нерешённый вопрос: **репозиторий git ещё не инициализирован.**
Проект существует как папка с двумя документами; перед написанием кода нужно
решение, заводить ли git здесь же.

Остальные развилки, всплывавшие при проектировании, закрыты внутри этого
документа: водяной знак — синтезированный маркер (раздел 5), лимиты загрузки —
таблица в разделе 4, откат при нехватке видеопамяти — на CPU (раздел 6).
