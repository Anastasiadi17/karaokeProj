# Окно гонки при удалении трека во время обработки — дизайн

Подсистема A (ядро обработки), 13 августа 2026. Закрывает последнее открытое
решение из списка, оставшегося после плана `2026-08-11-processing-core`
(пункт Д8 журнала).

---

## 1. Задача

### Точные границы окна

**Воркер** (`api/src/karaoke_api/jobs/runner.py`):

- строка 100 — `if self._store.get_track(job.track_id) is None` — трек ещё
  в базе, проходим дальше;
- строка 114 — `self._storage.store_file(key, path)` — пишем стемы.

Между ними — время копирования двух дорожек примерно по 100 МиБ.

**DELETE** (`api/src/karaoke_api/main.py`):

- строка 256 — `state.storage.delete_prefix(f"tracks/{track_id}")`;
- строка 265 — `state.store.delete_track(track_id)`.

Если DELETE целиком укладывается между строками 100 и 114, воркер уже после
`rmtree` заново создаёт `tracks/{id}/stems/*.wav`, а строки трека в базе
больше нет.

### Почему это плохо

Получившиеся файлы не видит никто:

- `GET /api/tracks/{id}/stems/{kind}` спрашивает базу и отдаёт 404;
- `purge_expired` перебирает строки таблицы `tracks`, а строки нет.

Подбирает их только `purge_orphan_track_dirs` — и только при старте
процесса. То есть на долгоживущем сервере файлы занимают диск неограниченно
долго.

### Почему нельзя просто перенести сверку каталогов в часовой цикл

`purge_orphan_track_dirs` удаляет каталоги, которым не соответствует строка в
базе. В пути загрузки трека такое состояние — нормальное и мгновенное:

```python
state.storage.store_file(key, staged)      # каталог уже есть
state.store.create_track(track_id, ...)    # строка появляется только тут
```

Сверка, запущенная в этом окне, снесёт только что принятый файл параллельной
загрузки. Поэтому она и живёт при старте, когда загрузок в полёте нет.

## 2. Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Горизонт | Один процесс — надолго | Архитектура явно однопроцессная: «GPU один, параллелить нечего». Значит, замок в памяти процесса — законное решение, а не костыль |
| Способ | Один замок вокруг двух критических секций | Окно не сужается, а исчезает: переплетения не существует. Около десяти строк, без правки схемы и контракта |
| Таймаут | Только у `DELETE` | Ждёт живой HTTP-клиент. У воркера и уборки альтернативы нет: сдавшийся по таймауту воркер либо пишет без замка (возвращая ту же гонку), либо теряет досчитанную задачу |
| Шум в логе | Классифицировать сбой | Удаление трека во время обработки — штатное действие пользователя, а не сбой сервиса |

Отклонено:

- **Мягкое удаление (`deleted_at`).** Правильно при нескольких воркерах, но
  это изменение схемы и семантики `DELETE` ради горизонта, который в MVP не
  наступает.
- **Компенсация постфактум** (записать стемы, перепроверить строку, убрать за
  собой). Три строки, но лечит следствие и оставляет окно на смерть процесса
  между записью и проверкой — то есть держится на той же подпорке, что и
  сегодняшний код.
- **Замок на трек вместо глобального.** Воркер один, одновременно пишется
  максимум один трек: выигрыш нулевой, а словарь замков надо чистить.

## 3. Замок

Новый модуль `api/src/karaoke_api/track_lock.py`:

```python
class TrackLockBusy(RuntimeError):
    """Замок не удалось взять за отведённое время."""


class TrackLock:
    def hold(self, timeout: float | None = None): ...   # контекстный менеджер
```

Без `timeout` ждёт сколько потребуется, с `timeout` бросает `TrackLockBusy`.

Отдельный модуль, а не поле в `JobStore` или `Storage`, потому что замок
охраняет именно **пару** «строка трека + его файлы» — то, что не принадлежит
ни базе, ни хранилищу по отдельности. Класть его в `cleanup.py` тоже нельзя:
тогда `runner.py` импортировал бы уборку, о которой знать не должен.

**Порядок захвата:** `TrackLock` всегда берётся до внутреннего замка
`JobStore` и никогда наоборот. `JobStore` о `TrackLock` не знает вовсе,
поэтому обратного порядка взяться неоткуда — взаимной блокировки не
возникает по построению.

## 4. Кто и что держит

### Воркер

Критическая секция в `_run_claimed` — «проверить строку → записать оба стема
→ `finish`». `finish` входит внутрь: тогда инвариант «стемы на диске ⟺
задача `done`» держится целиком, а не почти.

### Удаление

Новая функция в `cleanup.py`:

```python
def purge_track(store, storage, track_lock, track_id, timeout=None) -> None:
    with track_lock.hold(timeout):
        storage.delete_prefix(f"tracks/{track_id}")
        store.delete_track(track_id)
```

Ею пользуются оба удаляющих пути — обработчик `DELETE` и `purge_expired` в
часовом цикле. Сейчас эта пара продублирована в двух местах; после правки
останется одна.

`purge_expired` зовёт её **без таймаута** (`timeout=None`) и сохраняет свой
`try/except` вокруг каждого трека: один неудалимый трек не должен обрывать
всю уборку.

Поведение при сбое удаления файлов сохраняется: если `delete_prefix` бросил,
`store.delete_track` не вызывается и строка остаётся — иначе файлы стали бы
сиротами.

### Обработчик `DELETE`

Уходит в `asyncio.to_thread` целиком, иначе ожидание замка встало бы поперёк
событийного цикла. Берёт замок с таймаутом `track_lock_timeout_sec` и на
`TrackLockBusy` отвечает уже существующим `503 delete_failed`. Новых кодов в
контракте не появляется.

**`track_lock_timeout_sec = 30.0`** — новая настройка. Запись двух дорожек
занимает около секунды, то есть запас примерно тридцатикратный, и при этом
заметно меньше обычного таймаута HTTP-клиента.

## 5. Проводка

`AppState` получает поле `track_lock`. `JobRunner` — необязательный параметр
`track_lock`: если он не передан, раннер создаёт свой.

Параметр необязательный, чтобы не переписывать восемь мест в тестах, где
раннер конструируется напрямую. У этого решения есть характерный способ
сломаться молча: главный код забыл передать общий замок, у раннера свой,
гонка вернулась, все тесты зелёные. Поэтому отдельный тест закрепляет, что
`state.runner._track_lock is state.track_lock`.

## 6. Шум в логе

В `except`-ветке `_run_claimed` сбой классифицируется. Если строки трека уже
нет — это штатное удаление (исходник исчез из-под `materialize`), пишем
`log.info` с текстом исключения. Иначе — `log.exception` с полным traceback,
как сейчас.

Классификация идёт через вспомогательный `_track_is_gone`, который при любой
ошибке обращения к базе возвращает `False`: при выключении соединение может
быть уже закрыто, и тогда честнее считать трек живым и залогировать полно,
чем проглотить настоящий сбой.

**Оговорка:** если трек удалили *и* одновременно случился настоящий баг,
traceback будет понижен до `info`. Это принято сознательно — задачу
удалённого трека всё равно уже никто не наблюдает.

## 7. Тесты

1. **Настоящая гонка.** Обёртка `BlockingStorage` останавливает воркера
   внутри `store_file` — ровно в середине критической секции. Из другого
   потока запускается `purge_track`; проверяется, что он **не** завершился,
   пока воркер держит замок. После освобождения оба доходят, и не остаётся ни
   строки, ни каталога. Без замка удаление проходит сразу — тест краснеет.
2. **503 при занятом замке.** Замок держится извне, `DELETE` через
   `TestClient` с крошечным таймаутом отвечает `503 delete_failed`.
3. **Проводка.** `state.runner._track_lock is state.track_lock`.
4. **Лог без traceback.** DELETE между `claim_next` и `materialize`; через
   `caplog` проверяется, что записей уровня `ERROR` нет.

Существующий `test_delete_during_processing_leaves_no_files`
(`tests/test_cleanup.py:139`) остаётся: он проверяет другую ветку той же
машинерии — DELETE приходит, пока `SlowSeparator` ещё считает, и упирается в
проверку на строке 100. До остаточного окна он не достаёт по построению,
потому что окно живёт **после** `separate`.

## 8. Что не меняется

- `purge_orphan_track_dirs` при старте остаётся. Замок закрывает
  переплетение внутри процесса, но не случай «процесс умер между записью и
  удалением».
- Сверка каталогов по-прежнему не переносится в часовой цикл — причина в
  разделе 1.
- Схема базы, коды ответов и контракт с подсистемой B не трогаются.

---

## 9. Что в задачу не входит

- Мягкое удаление и подготовка к нескольким воркерам. Понадобится вместе с
  переездом очереди на Redis, а не раньше.
- Отмена работающей задачи при `DELETE`. Сейчас задача досчитывает и молча
  выбрасывает результат; прерывать `apply_model` на середине незачем —
  экономия секунд GPU против нового пути отказа.
- Устранение `503 delete_failed` для занятых файлов на Windows. Замок его не
  затрагивает: `materialize` в критическую секцию не входит, иначе `DELETE`
  ждал бы всю обработку.
