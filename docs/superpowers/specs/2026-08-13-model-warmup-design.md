# Прогрев модели при старте — дизайн

Подсистема A (ядро обработки), 13 августа 2026. Закрывает открытое решение
№1 из списка, оставшегося после завершения плана `2026-08-11-processing-core`.

---

## 1. Задача

Шапка плана подсистемы A утверждает: «Модель demucs загружается один раз при
старте и остаётся в памяти». Диаграмма потока данных в спеке
`2026-08-11-karaoke-mvp-architecture-design.md` подписывает раннер тем же —
«(модель уже в памяти)». Код грузит модель лениво, в `_ensure_model`, на
первой задаче. Утверждение неверно в двух документах сразу, а `/api/health`
называется проверкой готовности и о модели не знает ничего.

### Цена вопроса — не та, что записана в открытом решении

Заметка о решении говорила про «холодные ~24 с у первого пользователя». После
замера на двух длительностях (см. `karaoke-context.md` 4.5) это неверно.
Издержки распадаются на две разные величины:

| Издержка | Величина | Когда наступает |
|---|---|---|
| Загрузка весов из локального кеша + перенос на GPU | ≈2,6 с | первый вызов `_ensure_model` **в процессе** |
| JIT-компиляция ядер CUDA/cuDNN | ≈20 с | первый настоящий `apply_model` **на машине или в контейнере** |

На постоянно работающем сервере первый пользователь платит 2,6 с. На свежем
контейнере RunPod — обе, около 23 с. Прогрев переносит их со случайного
первого запроса на предсказуемый момент старта процесса; вторую издержку он
устраняет только внутри процесса, кеш ядер на диске он не наполняет заранее.

### Сопутствующий дефект

`_ensure_model` (`api/src/karaoke_api/separation/demucs_local.py`) не
синхронизирован. Сейчас это безопасно ровно потому, что вызывает его
один-единственный рабочий поток раннера, — инвариант нигде не записан. Любой
прогрев вне этого потока превращает латентный дефект в настоящий: две
параллельные загрузки модели, лишние секунды и лишняя видеопамять.

## 2. Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Цель | Честная готовность | Прогрев фоновый, старт не блокируется; снаружи видно, готов сервис или нет |
| Код ответа `/api/health` | Всегда 200, состояние — поле в теле | Эндпоинт остаётся диагностическим. Оркестратора, читающего код ответа, нет; 503 в браузере у человека выглядит как сломанный сервис |
| Глубина прогрева | Веса **и** пробный инференс (инференс — только на CUDA) | Только веса сняли бы 2,6 с из примерно 23. Оговорка: короткий тензор прогоняет большую часть ядер, гарантировать все нельзя |
| Отказ прогрева | Лог + `failed` в health, сервис работает | Та же линия, что у `check_gpu`, который по контракту не валит старт ни при каких обстоятельствах |
| Где крутится прогрев | В рабочем потоке раннера | Гонка исчезает по построению, а не починкой |

Отклонено: блокировать приём трафика до прогрева (удлиняет cold start на
RunPod, не убирая его); отдельный фоновый поток из `lifespan` (требует
синхронизации ради выигрыша в миллисекунды); прогрев по первому обращению к
`/api/health` (готовность зависела бы от того, посмотрел ли кто-то на
эндпоинт); отдельный эндпоинт `/api/ready` (потребителя не существует).

## 3. Архитектура

`JobRunner.run_forever` перед входом в цикл опроса один раз прогревает
разделитель — в том же пуле потоков, где считаются задачи:

```
lifespan → create_task(runner.run_forever())
              │
              ├─ to_thread(_warmup)       pending → loading → ready | failed
              │     separator.warmup()    ≈2,6 с веса + компиляция ядер
              │
              └─ while not stopped: to_thread(run_once)    ← цикл опроса
```

Событийный цикл в это время свободен: HTTP-запросы принимаются с первой
секунды. Задача, поставленная во время прогрева, дождётся его в очереди — ей
модель всё равно нужна. Модели касается ровно один поток за всю жизнь
процесса.

## 4. Компоненты

### `separation/base.py`

Протокол `StemSeparator` получает метод:

```python
def warmup(self) -> None: ...
```

Контракт: идемпотентен, безопасен при повторном вызове, реализации без модели
не делают ничего. Метод обязательный, а не опциональный: новая реализация
разделителя не должна иметь возможности молча его пропустить.

### `separation/fake.py`

`FakeSeparator.warmup` — пустой. Подделка готова всегда, и это честно: греть
нечего.

### `separation/demucs_local.py`

- `threading.Lock` вокруг загрузки в `_ensure_model`, схема double-checked:
  проверка → замок → повторная проверка → загрузка. Комментарий фиксирует
  инвариант «модели касается только рабочий поток раннера» и объясняет, что
  замок страхует будущее, а не чинит настоящее.
- `warmup()` вызывает `_ensure_model()`, затем — **только при
  `device == "cuda"`** — прогоняет пробный тензор через
  **`_apply_with_fallback`**, тот же путь, которым идут настоящие задачи.
  Прогрев через другой путь прогрел бы не те ядра.
- **На CPU пробного инференса нет.** Он существует ради компиляции ядер
  CUDA, а на процессоре этой издержки не бывает: остаётся только создание
  примитивов oneDNN, это миллисекунды. Прогон же пяти секунд через htdemucs
  на CPU стоит десятки секунд и не покупает ничего. Побочно это удерживает
  быстрый набор: `test_unavailable_gpu_at_startup_makes_the_app_use_cpu`
  поднимает настоящий `DemucsSeparator` с `device="cpu"`, и такой прогрев
  сделал бы «быстрый» тест минутным.
- Вход прогрева — `torch.zeros(2, int(WARMUP_SECONDS * model.samplerate))`,
  `WARMUP_SECONDS = 5.0` константой модуля с обоснованием: пять секунд стоят
  ≈0,15 с счёта и при этом попадают в обычную сегментную ветку `apply_model`,
  а не в вырожденную.

### `jobs/runner.py`

```python
@dataclass(frozen=True)
class WarmupStatus:
    state: str                      # pending | loading | ready | failed
    detail: str | None = None       # причина отказа
    elapsed_sec: float | None = None
```

`detail` заполняется только при `failed`. `elapsed_sec` заполняется при
`ready` и при `failed` (сколько прошло до отказа), при `pending` и `loading`
равен `null`.

- Поле в `JobRunner`, начальное значение `WarmupStatus("pending")`.
- Свойство `warmup_status` на чтение из событийного цикла. Замок не нужен:
  публикуется неизменяемый объект целиком, а присваивание ссылки в CPython
  атомарно.
- Метод `_warmup()`: ставит `loading`, вызывает `separator.warmup()`, ставит
  `ready` с временем; на исключении — `failed` с `f"{type(exc).__name__}:
  {exc}"` и `log.exception`.
- `run_forever` вызывает `await asyncio.to_thread(self._warmup)` перед циклом,
  пропуская прогрев, если раннер уже остановлен.

Статус живёт у раннера, потому что раннер владеет потоком, который его пишет.
`GpuStatus` лежит в `app.state` как раз потому, что пишется однократно до
старта и больше не меняется.

### `main.py`

`/api/health` получает третий ключ; существующие не меняются:

```json
{
  "gpu": {"available": true, "device_name": "…", "reason": null, "hint": null},
  "separator": "demucs",
  "model": {"state": "ready", "detail": null, "elapsed_sec": 3.1}
}
```

Поле добавляется, а не заменяет что-либо: `/api/health` не используется планом
подсистемы B, контракт между подсистемами изменение не задевает.

## 5. Ошибки и краевые случаи

1. **Прогрев упал** (весов нет в кеше и нет сети, битый кеш, сломанный CUDA) →
   `failed` с типом и текстом исключения в `detail`, `log.exception`, цикл
   опроса продолжает работать. Задача упадёт на том же `_ensure_model` и
   получит честную причину в поле `error`.
2. **Прогрев ушёл в откат на CPU** — OOM на пяти секундах тишины означает, что
   что-то серьёзно не так. Пишется warning, состояние всё равно `ready`.
   Пометка `degraded` у задач от прогрева не зависит: `warmup` не создаёт
   `SeparationResult`.
3. **Выключение во время прогрева** — `task.cancel()` снимает ожидание
   `to_thread`, но поток дозагружает модель. Базы прогрев не касается, терять
   нечего; процесс подождёт поток на выходе, сверху это ограничено временем
   загрузки. Записывается в docstring явно.
4. **`separator=fake`** → `ready` мгновенно. Быстрые тесты и разработка без GPU
   не удлиняются.
5. **GPU недоступен** — сепаратор уже собран с `device="cpu"` (вердикт
   `check_gpu` выбирает устройство). Прогрев ограничивается загрузкой весов,
   пробного инференса нет: компилировать нечего. Первая задача на CPU и так
   идёт в десятки раз дольше, экономить на её фоне нечего.
6. **`uvicorn --reload`** — прогрев на каждый перезапуск, в фоне; ввод
   разработчика не блокирует.

## 6. Тесты

Быстрые, без GPU:

1. `warmup()` вызван до первой заявки задачи — подделка записывает порядок
   вызовов.
2. Падение прогрева не останавливает цикл: подделка с бросающим `warmup()` →
   задача всё равно доходит до `done`, `warmup_status.state == "failed"`, в
   `detail` тип и текст исключения.
3. `/api/health` отдаёт `model.state == "ready"` при `separator=fake`.
4. `warmup_status` до запуска цикла — `pending`.

Медленный, под маркером `slow`:

5. `DemucsSeparator().warmup()` заполняет `_model`; последующий `separate()`
   использует тот же объект модели, а не загружает заново. Печатает время
   прогрева.

Побочно: тестовые подделки `ExplodingSeparator` (`tests/test_runner.py`) и
`SlowSeparator` (`tests/conftest.py`) получают `warmup`.

## 8. Что в задачу не входит

- Наполнение дискового кеша ядер CUDA при сборке образа RunPod. Это устранило
  бы вторую издержку (≈20 с) для свежего контейнера, но относится к
  развёртыванию, а не к ядру обработки.
- Отказ в приёме треков при `state == "failed"`. Потребовал бы нового кода
  ошибки в контракте с подсистемой B и рисковал бы отказывать из-за разового
  сбоя, после которого ленивая загрузка сработала бы.
- Повторные попытки прогрева. Задача сама попробует загрузить модель через
  тот же `_ensure_model`; отдельный механизм повторов дублировал бы это.
