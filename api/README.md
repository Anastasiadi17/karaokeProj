# Karaoke API

Ядро обработки: принимает трек, отделяет минусовку через demucs, отдаёт дорожки.

## Установка

Нужен Python 3.12 — колёса PyTorch под 3.14 могут отсутствовать.

    py -3.12 -m venv .venv
    .venv/Scripts/python -m pip install -e ".[dev]"
    .venv/Scripts/python -m pip install torch torchaudio --index-url https://download.pytorch.org/whl/cu128
    .venv/Scripts/python -m pip install -e ".[gpu]"

Индекс `cu128` обязателен: RTX 5060 — архитектура Blackwell (sm_120), обычная
сборка PyTorch на ней не запускается. Группа `gpu` из `pyproject.toml`
допускает и уже проверенные версии (`torch 2.11.0+cu128`, `demucs 4.1.0`) —
ставить torch/torchaudio отдельно нужно именно из-за индекса cu128, иначе
встанет несовместимая CPU-сборка.

Проверить GPU настоящим вычислением, а не только `is_available()` (см.
`karaoke_api/gpu.py` — `zeros()` проходит и на несовместимой сборке, потому
что заполнение нулями уходит в `cudaMemsetAsync`, а не в вычислительное ядро):

    .venv/Scripts/python -c "import torch; print((torch.ones(8, device='cuda') * 2).sum().item())"

Ожидается `16.0`. Если падает с `no kernel image` — сборка не та, переустановить под индексом cu128.

## Запуск

    cp .env.example .env
    .venv/Scripts/python -m uvicorn karaoke_api.main:app --reload

Проверка готовности: <http://127.0.0.1:8000/api/health>

Эндпоинт отвечает всегда 200. Поле `model.state` показывает прогрев модели:
`loading` в первые секунды после старта, дальше `ready`. `failed` означает,
что прогрев не удался (причина — в `model.detail`); сервис при этом
работает, но задачи, скорее всего, будут падать по той же причине.

Перед выставлением наружу периметр (nginx/Cloudflare) обязан ограничивать
размер тела запроса — `client_max_body_size 200m` или эквивалент: приложение
отвергает запрос по `Content-Length` до разбора формы, но само тело до него
всё равно доезжает. Значение должно совпадать с `KARAOKE_MAX_UPLOAD_BYTES`
(по умолчанию 200 МиБ): если периметр строже, отказ придёт раньше приложения
и с чужим текстом, если мягче — защита периметра не работает.

Заложите временный диск из расчёта двух размеров загрузки на каждую
параллельную: тело сначала оседает в спуле multipart, потом копируется в
рабочий каталог.

## Одинаковый источник вместо CORS

Сервис рассчитан на то, что браузер и API всегда видны с одного origin.
Поэтому `CORSMiddleware` сюда сознательно не подключён: кросс-доменных
запросов нет вовсе, а `CORSMiddleware` только расширил бы поверхность атаки
без всякой пользы.

Один origin получается тремя способами, и выбирать надо по обстоятельствам:

1. **Разработка.** `web/` проксирует `/api` через Vite на этот бэкенд
   (`http://127.0.0.1:8000`). Ничего настраивать не нужно.
2. **Всё одним процессом.** Собрать фронт и указать каталог сборки:

        cd ../web && npm run build
        cd ../api && KARAOKE_WEB_DIST=../web/dist \
            .venv/Scripts/python -m uvicorn karaoke_api.main:app

   Тогда `/` отдаёт студию, `/api/*` — API, и запускать больше нечего.
   Кратчайший путь показать продукт целиком; сквозные сценарии подсистемы B
   гоняются и против такой сборки:

        cd ../web && KARAOKE_E2E_BASE_URL=http://127.0.0.1:8000 npm run test:e2e

3. **Обратный прокси** (nginx/Cloudflare) перед обоими. Нужен там, где и так
   стоит периметр: он же ограничивает размер тела (см. выше) и отдаёт
   статику эффективнее, чем `StaticFiles`. Тогда `KARAOKE_WEB_DIST` не
   задаётся.

В корне репозитория лежат `Dockerfile` и `compose.yaml` для второго способа:
образ собирает фронт и запускает API с уже выставленным `KARAOKE_WEB_DIST`.
**Оба ни разу не собирались** — в среде, где они написаны, недоступен демон
Docker; относитесь к ним как к черновику, который надо один раз прогнать и
поправить. Список того, что проверить при первой сборке, — в конце
`Dockerfile`. Для RunPod Serverless нужен другой вход (их handler вместо
uvicorn), и он пока не спроектирован.

Пустой `KARAOKE_WEB_DIST` — поведение по умолчанию: API не раздаёт ничего,
кроме `/api/*`. Если путь указан, а каталога нет, сервис поднимается и пишет
предупреждение в лог: фронт просто не собран, API от этого не бесполезен.
Клиентских маршрутов у студии нет, поэтому неизвестный адрес отвечает 404, а
не подсовывает `index.html`.

## Обработка на RunPod

    KARAOKE_SEPARATOR=runpod
    KARAOKE_RUNPOD_ENDPOINT=https://api.runpod.ai/v2/<id>
    KARAOKE_RUNPOD_API_KEY=...

Требует `KARAOKE_STORAGE=r2` и отказывается стартовать без него: воркер живёт
на чужой машине, локальный диск ему недоступен, и молчаливый откат дал бы
задачи, падающие на скачивании исходника, — а виноватым выглядел бы RunPod.

Образ воркера — `Dockerfile.worker` в корне репозитория.

## Воркер RunPod

`karaoke_api.worker.handler` — точка входа для serverless: забирает исходник
по подписанной ссылке, гоняет тот же demucs, кладёт дорожки по подписанным
ссылкам на запись. Ни базы, ни очереди, ни знания о пользователях — это
остаётся у всегда включённого API.

Ссылки приходят готовыми и здесь не строятся: воркер не должен уметь ходить
по произвольному адресу, иначе наш GPU по чужой просьбе качает что угодно
откуда угодно.

Запуск в контейнере воркера:

    python -m karaoke_api.worker.handler

Против настоящего RunPod не выполнялось: ни аккаунта, ни пула в среде нет.
Тело вынесено в `separate_job` — оно проверяется тестами без их SDK и без GPU.

## Хранилище

По умолчанию файлы лежат на диске рядом с процессом. Объектное включается
настройкой:

    KARAOKE_STORAGE=r2
    KARAOKE_R2_ENDPOINT=https://<account>.r2.cloudflarestorage.com
    KARAOKE_R2_BUCKET=...
    KARAOKE_R2_ACCESS_KEY=...
    KARAOKE_R2_SECRET_KEY=...

Неполная настройка — отказ на старте, а не тихий откат на диск: молчаливый
откат хуже падения, потому что файлы лягут туда, где их не найдёт обработка
на чужой машине.

Локальное хранилище годится ровно до тех пор, пока обработка живёт в том же
процессе. Воркеру RunPod диск недоступен — см. дизайн serverless.

R2 против настоящего сервиса не прогонялся: ключей в среде разработки нет.

## Воронка

Считается пять шагов: попросил ссылку, вошёл, загрузил трек, записал дубль,
скачал микс. Два последних видит только браузер и сообщает их сам.

Отчёт закрыт токеном — числа воронки это бизнес-показатели, отдавать их
любому вошедшему незачем:

    KARAOKE_METRICS_TOKEN=...
    curl -H "x-metrics-token: ..." http://127.0.0.1:8000/api/funnel

Пусто — отчёт отвечает 503, но события всё равно пишутся. Собирать их надо с
первого дня: первые дни воронки не восстановить задним числом.

Считаются РАЗНЫЕ люди, а не нажатия: конверсия — это доля людей. Удаление
аккаунта историю не переписывает, иначе вчерашняя воронка менялась бы при
каждом уходе.

## Логи

По умолчанию — человеческий текст. На сервере включается JSON:

    KARAOKE_LOG_JSON=true

Тогда каждая запись становится объектом с полями `ts`, `level`, `logger`,
`message`; всё, что передано через `extra=`, попадает туда же отдельными
полями — по `track_id` можно сгруппировать, по строке текста нельзя.
Traceback уходит одним полем `exception`, а не двадцатью несвязанными
строками, как его разберёт любой сборщик логов.

Подробность правится `KARAOKE_LOG_LEVEL` без пересборки.
